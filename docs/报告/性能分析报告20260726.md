# SuperFactory 集成工厂性能分析报告

> 分析日期: 2026-07-26
> 分析对象: `profile-2026-07-26_12.47.10.sparkprofile`
> 场景: 40 个纯产出节点，每秒千万级物品/流体产出
> 总耗时: 2360μs/tick (2.36ms/tick)

---

## 1. 总体结论

在 40 节点纯产出场景下，`MTESuperIntegratedFactory.onPostTick` 单 tick 耗时约 **2360μs**，而原版 GT 多方块在同等产出量下加起来不到 1000μs。问题不在外部 IO（已在上一轮解决），而在于**调度器内部的算法复杂度**——每 tick 对全部 40 个节点重复进行分类、并行计算、节流判断、低水位计算等操作。

spark profile 解析共识别到 **311 个 SuperFactory 相关方法**被频繁调用，主要热点集中在以下链路上。

---

## 2. 热点链路分析

### 2.1 核心调用链

```
onPostTick (2360μs)
  └─ processRunningMode
       ├─ buildRuntimeResourceSnapshot     ← 每 tick 重建完整快照
       │    ├─ captureInternalItems         ← List 线性扫描
       │    ├─ captureLiveItems             ← 遍历输入舱
       │    ├─ captureDualInputs            ← 遍历双输入舱
       │    └─ captureIncomingWithinLookahead ← 遍历 runningJobs
       ├─ flushOutputBuffers               ← 每 tick flush
       ├─ advanceRunningJobs               ← 遍历 runningJobs
       └─ scheduleRunnableNodes            ← 调度器
            └─ buildNodeCandidates (×5 次 per layer)
                 ├─ classifyCandidateLayer
                 │    ├─ consumesAvailableInternalInput
                 │    ├─ suppliesLowWater   ← 运行时扫描 runtimeEdges
                 │    └─ producesTargetOutput
                 ├─ effectiveParallelLimit   ← 反复读取 parameters
                 ├─ effectiveDurationTicks   ← 反复计算 OC
                 ├─ getRunnableParallel     ← 遍历输入槽 + 快照查询
                 ├─ isExternalOutputThrottled ← 遍历输出槽 + 水位判断
                 ├─ distanceToTerminal      ← 递归图遍历
                 └─ runCredit               ← Map 查询
```

### 2.2 关键发现

spark profile 的 method table 显示了大量重复注册——同一方法被多次采样在不同调用路径下：
- `MaterialKey.ofItem` / `MaterialKey.hashCode` / `MaterialKey.equals`: 在多个路径下反复计算
- `RuntimeRouteResolver.resolve`: 输出路由在每个节点的每个输出上反复调用
- `getStackAmount` / `getDisplayAmount`: 每个节点的每个槽位反复解析
- `IntegratedFactoryWatermarks.*`: 每次 `suppliesLowWater` 触发全边扫描
- `shouldThrottleInternalItemOutput` / `shouldThrottleInternalFluidOutput`: 每个候选节点都调用
- `NGTTagCompound.func_74778_a` (getString): 每次 `getParametersField` 都触发 NBT 读取

## 3. 复杂度和瓶颈分析

### 3.1 当前复杂度模型

```
O(layerCount(5) × nodeCount(40) × (slotsPerNode × snapshotQuery + edgeScan + throttleCheck + routeResolve))
```

每组乘数：
- **5 层 × 40 节点 = 200 次分类判断/tick**
- 每次分类触发 `consumesAvailableInternalInput` + `suppliesLowWater` + `producesTargetOutput`
- `suppliesLowWater` 中最昂贵的 `getInternalItemLowWater` 每次调用扫描全部 runtimeEdges 和 consumer inputs
- `isExternalOutputThrottled` 遍历所有 output slots 并查询 buffer

### 3.2 实际瓶颈分布 (估算)

| 热点区域 | 估算占比 | 问题性质 |
|---------|---------|---------|
| 5 次全图扫描 (buildNodeCandidates ×5) | ~40% | 架构问题 |
| suppliesLowWater (边扫描+水位计算) | ~20% | 可预编译 |
| RuntimeResourceSnapshot 线性扫描 | ~15% | 可索引化 |
| MaterialKey 反复创建/hash/equals | ~10% | 可缓存 |
| 输出节流判断 (isExternalOutputThrottled) | ~10% | 可预编译 |
| flushOutputBuffers | ~5% | 可优化预算 |

## 4. 优化方案

### P0：一次全图扫描 + CandidateLayer 分桶

**当前问题**: `IntegratedFactoryScheduler.schedule()` 对每个 `CandidateLayer` 调用一次 `buildNodeCandidates()`，导致 5 次全图遍历。

**方案**: 改为一次遍历所有节点，每个节点只分类一次，然后按 layer 分桶。

```java
// 当前 (5 次扫描):
for (CandidateLayer layer : CandidateLayer.values()) {
    for (NodeCandidate candidate : buildNodeCandidates(ctx, layer)) { ... }
}

// 优化后 (1 次扫描):
EnumMap<CandidateLayer, List<NodeCandidate>> buckets = new EnumMap<>(...);
for (ProcessNode node : ctx.schedulingOrder()) {
    NodeCandidate candidate = analyzeNodeOnce(ctx, node);
    buckets.get(candidate.layer).add(candidate);
}
for (CandidateLayer layer : CandidateLayer.values()) {
    for (NodeCandidate candidate : buckets.get(layer)) { ... }
}
```

**预期收益**: 40% 耗时削减 (~944μs)
**语义风险**: 低（保持同层排序、启动顺序不变）

### P1：TickNodeAnalysis 缓存

**当前问题**: 同一 tick 内，同一节点的 `effectiveParallelLimit`、`effectiveDurationTicks`、`runnableParallel`、`distanceToTerminal`、`candidateLayer` 被反复计算。

**方案**: 引入 `TickNodeAnalysis` 对象，同一 tick 内每个节点只分析一次。

```java
class TickNodeAnalysis {
    ProcessNode node;
    CandidateLayer layer;
    int effectiveParallelLimit;
    int effectiveDurationTicks;
    int runnableParallel;
    boolean externalOutputThrottled;
    int distanceToTerminal;
    double runCredit;
}
```

**预期收益**: 进一步削减 15-20% 耗时
**语义风险**: 低（可在启动前用 `canStartNode` 做硬校验）

### P2：水位预编译 + RuntimeResourceSnapshot 索引化

**当前问题**: `suppliesLowWater` 每次调用运行时扫描所有 edges 和 consumer inputs。
RuntimeResourceSnapshot 用 `List<BufferedItemStack>` 做线性查询。

**方案**:
- 水位 lowWater/highWater 在图提交或参数变化时预编译到 `CompiledWatermarkInfo`
- Snapshot 内部增加 `Map<MaterialKey, Long>` 索引

**预期收益**: 进一步削减 25-35% 耗时
**语义风险**: 中（需要正确失效机制）

### P3：材料键缓存 + 编译槽

**当前问题**: `MaterialKey.ofItem()` 每 tick 被调用数百次，每次都做 `GTUtility.getFluidFromDisplayStack` + NBT hash。

**方案**: 在图提交时预编译 `CompiledInputSlot` / `CompiledOutputSlot`。

**预期收益**: 削减 10% 耗时
**语义风险**: 中（需在配方变化时失效）

### P4：flushOutputBuffers 预算优化

**当前问题**: 每 tick flush 输出，在产出量千万级时 flush 量巨大。

**方案**: 增大单 tick flush 最大量 + 可配置的 flush 频率。

**预期收益**: 削减 5% 耗时
**语义风险**: 低

---

## 5. 推荐实施顺序

| 优先级 | 优化项 | 预期累计 | 风险 |
|-------|--------|---------|------|
| **P0** | 一次全图扫描 + 分桶 | ~1500μs | 低 |
| **P1** | TickNodeAnalysis 缓存 | ~1200μs | 低 |
| P2 | 水位预编译 + 快照索引 | ~800μs | 中 |
| P3 | 材料键缓存 + 编译槽 | ~600μs | 中 |
| P4 | flush 预算优化 | ~550μs | 低 |

**目标**: P0+P1 完成后从 2360μs 降至 ~1200μs，接近原版 GT 多方块水平。

---

## 6. 语义保持不变的关键不变量

所有优化必须遵循：
1. `CandidateLayer` 优先级顺序不变
2. 每层内部排序规则不变 (runCredit desc, targetDistance asc, nodeId asc)
3. `maxNodeStartsPerTick` 限制不变
4. `tryStartNodeCandidate` 启动前硬校验保留
5. 事务性输入扣除 (consumeNodeInputs) 保留
6. 高/低水位滞回状态机保留
7. cycle reserve 规则保留
